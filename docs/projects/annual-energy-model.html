Annual Building Energy Consumption Modeling

A learned stand-in for dynamic thermal simulation — milliseconds instead of minutes per building, with a measured and reproducible gap to the physics it replaces. In production

The model was the least uncertain part of this project. Everything expensive lived in manufacturing a training set you could trust.

This page describes the engineering approach at a high level. Source code, customer data and proprietary implementation details remain private.

Problem

Estimating a building's annual heating and cooling demand properly requires dynamic thermal simulation: a physics engine, a fully specified building, and minutes of compute per variant. That is far too slow to sit behind an interactive product, and it cannot be run across a portfolio of assets on demand.

The goal was a surrogate: something that reproduces the simulator's answer in milliseconds, across climate zones and countries, with a measured gap to the physics it replaces.

Context

The training data does not exist in the wild — it has to be manufactured. That makes this as much a data-generation and orchestration problem as a modeling one: sample a plausible building population, simulate every sample, collect the results, and only then train. Each stage fails on its own schedule, and a simulation run is expensive enough that silently losing or corrupting results is the main risk.

Architecture

Geography is first-class throughout — continent → country → climate zone, with a worldwide zone registry and country groups — so adding a country is configuration rather than code.

Engineering decisions

Versioning is separate for data and for models

A dataset version and a training version are independent labels. Retraining on an existing dataset, and regenerating data for an unchanged trainer, are both first-class operations instead of a destructive overwrite. Manifests record generated samples, simulation results and per-zone datasets, with SHA-256 fingerprints of the code that produced them. This is what makes a six-month-old run explainable.

A local model registry, independent of the tracking server

Releases are snapshotted into a registry and compared to the previous release for the same country. Comparison emits Markdown, CSV and JSON reports plus a PDF of prediction scatter plots — so “is the new model better?” has a reproducible artifact rather than a recollection. Release can fire automatically at the end of a country's training.

Metrics chosen for the decision they inform

Beyond MAE and R², evaluation reports the share of predictions within ±1 / ±5 / ±10 kWh, a mean relative error capped so near-zero denominators cannot dominate, and the share of predictions inside a ±5 % margin. An aggregate R² hides exactly the failure mode that matters here — a small set of buildings being badly wrong. Relative and absolute error are also reported per chunk and as bias box-plots, which surfaces systematic bias by building regime instead of averaging it away.

A GPU training path that does not change the serving artifact

An experimental trainer fits the network in PyTorch on GPU — batch-norm, large batches, the dataset resident in VRAM — then folds batch-norm and target de-normalisation into the final layer and transplants the weights into a strictly equivalent scikit-learn estimator. Training speed, same deployment surface.

Evaluation

  • Train / validation / test splits per zone, fixed seed.
  • MAE, R², capped mean relative error, in-margin rate, error distributions, predicted-vs-true scatter, per-chunk bias.
  • Version-to-version comparison against a shared reference dataset, with an explicit status per zone and target rather than one headline number.
  • Unit tests covering the versioning, release and comparison logic.

Quantitative results are internal and are not published here.

Technologies

Python · scikit-learn · PyTorch · NumPy · pandas · SciPy · Prefect · MLflow · Pydantic · joblib · Matplotlib · pytest · Docker · Poetry · loguru

What I took from it

  • Generating the dataset is the project.
  • Reproducibility has to be designed in, not added. Separating dataset and training versions, and fingerprinting the code, is what made old runs explainable.
  • A comparison report beats a metric. The release-vs-previous artifact is what actually gets used when deciding to ship.
